# T1 rolling deployment spike report

## Decision

Use a Deployment rolling update with `maxUnavailable: 0` and `maxSurge: 1`,
but treat rollout as a controller transaction:

1. run and wait for the release Job;
2. apply the candidate spec;
3. wait for rollout completion with a bounded timeout;
4. on failure, server-side apply the saved active spec with the same field
   manager and `--force-conflicts`, then wait for that rollout.

Do not use `kubectl rollout undo` as the automated recovery primitive. In the
failed-readiness test it reported that it rolled back, but the Deployment still
desired `VERSION=v2, READY=false`, retained one NotReady candidate pod, and
remained `ProgressDeadlineExceeded`. Applying the saved v1 spec restored one
desired/ready v1 replica in less than one second.

## Recommended P2 parameters

| Parameter | Value | Reason |
| --- | ---: | --- |
| `maxUnavailable` | `0` | keeps the active pod serving until a candidate is Ready |
| `maxSurge` | `1` | allows one candidate alongside the active singleton |
| `progressDeadlineSeconds` | `45` | deterministically detected permanent NotReady at 45 s |
| `terminationGracePeriodSeconds` | `45` | completed a 30 s request; WS termination occurred at about 43.84 s |
| readiness initial delay | `1 s` | app is local and starts quickly |
| readiness period | `2 s` | candidate became eligible quickly without busy polling |
| readiness timeout | `1 s` | bounds a stuck probe |
| readiness failure threshold | `3` | removes an unhealthy endpoint in at most about 6 s |
| readiness success threshold | `1` | admits a healthy candidate after its first success |
| `preStop` drain delay | `3 s` | avoided the SIGTERM/endpoint-removal race observed without it |
| rollout status timeout | `50 s` | exceeds the 45 s progress deadline without adding a long second timeout |

P2 should make the grace period workload-configurable when requests longer
than 30 s are supported. The value must exceed the maximum admitted request
duration plus shutdown overhead.

## Results

### 1. Ready rollout v1 to v2

Final isolated control at 200 target rps for 60 s and 50 concurrent
WebSockets:

- rollout status completed in 3 s;
- HTTP: 11,790 responses, 0 HTTP failures, 210 requests not generated by
  `hey`, p50 29.7 ms, p99 166.7 ms;
- all 50 WS connections closed with code 1006 about 43.84 s after the
  Kubernetes `Killing` event, within the 45 s grace period;
- reconnect succeeded: `totalOpened=100`, `maxConcurrent=50`,
  `disconnects=50`.

Without `preStop`, the first isolated run produced one HTTP 5xx and one missing
response. Adding a 3 s drain delay removed HTTP failures in two subsequent
rollouts. The host still did not always generate the full target volume, so the
repository script reported nonzero `drops` from its `missing_responses`
component even when every generated response succeeded. The strict
`drops=0` exit criterion was therefore not met; response-level zero-drop
semantics were met after adding `preStop`.

### 2. Thirty-second in-flight request

The final isolated rollout started two seconds after `/sleep?seconds=30`. The
request returned HTTP 200 with body `v2 slept 30s` after 30 s. It was not cut
off before grace.

### 3. Permanently NotReady v2 and recovery

The candidate reached `ProgressDeadlineExceeded` at the configured 45 s. The
active v1 remained the only Ready endpoint. During 55 s at 200 target rps it
served all 10,984 generated responses successfully; there were 0 HTTP failures
and 16 requests not generated by the fixed-rate client relative to 11,000.

`rollout undo` did not remove the broken desired state. Reapplying the saved v1
spec with `field-manager=t1 --force-conflicts` converged to one v1 desired and
Ready replica in less than one second.

### 4. Rollback as a normal v2 to v1 rollout

Final isolated rollback completed in 2 s and converged to one desired/Ready v1
pod. At 200 target rps for 60 s it returned 11,988 successful responses with 0
HTTP failures, 12 requests not generated by `hey`, p50 24.7 ms, and p99 69.5
ms. An earlier 70 s run also had 0 HTTP failures but generated 13,601/14,000
requests. Rollback response semantics are zero-drop; the strict load-script
`drops=0` criterion was not met because achieved request generation was below
the configured target.

### 5. Interrupted apply and idempotence

The apply process was terminated with exit 143. Repeating the same server-side
apply converged both Deployments to v2 with one desired and Ready replica each.
The ReplicaSet count stayed 6 to 6; no duplicate workload or garbage resource
was created.

### 6. Failed release Job

The Job exited nonzero and reached `Failed` with one failed pod. The guarded
command chain exited 1. Deployment generation stayed 7 to 7, proving that the
rollout did not start.

### 7. OOM after readiness

Ready v2 was limited to 64 MiB and `/oom` triggered allocation. Kubernetes
reported `OOMKilled`, exit 137, restart count 1, and a readiness `Unhealthy`
event before the container restarted. During 40 s at 200 target rps:

- 7,710 responses, 360 HTTP failures, 290 missing responses;
- p50 25.3 ms, p99 265.0 ms.

`maxUnavailable: 0` only protects a rollout transition. It cannot preserve
availability when the sole active replica crashes after becoming Ready. P2
must use at least two steady-state replicas for crash availability and alert on
container restart count, `lastState.terminated.reason=OOMKilled`, unavailable
replicas, and warning events.

## Exit criteria

- Generated HTTP responses during ready rollout and rollback: pass, 0 failures
  with the 3 s drain delay.
- Literal `load.sh drops=0`: fail, because `hey` under-generated 210 and 12
  requests in the final controls.
- WS disconnect within grace and reconnect: pass.
- Deterministic failed-rollout detection and removal of broken desired state:
  pass with saved-spec SSA recovery; fail with `rollout undo`.
