# T4: rootless BuildKit spike

## Result

Rootless BuildKit built, pushed, and returned a pullable manifest for 12 of 13 service build paths. The one failure is `railpack-pnpm-workspace/web`: Railpack 0.30.1 emits the configured `pnpm` build command in a stage where `pnpm` is absent. It failed identically on cold and warm runs (`pnpm: not found`), so this is a Railpack/client-path compatibility issue, not a rootless failure. G0 must either fix that production path or accept it as an explicit exception.

The run used `moby/buildkit:v0.30.0-rootless`, Railpack 0.30.1, k3d 5.8.3, k3s 1.31.5, and the public `buildDockerImage` export from `packages/docker`. Direct `buildctl` was used only for `du`/`prune` and the deliberately invalid Dockerfile, which the public client cannot describe without adding a fake example.

The requested VM is Linux/amd64, while `spike/env/doctor.sh` only accepts Homebrew, Colima, and arm64. `vm-bootstrap.sh` installs the pinned Linux tools and supplies a temporary doctor adapter over the native Docker daemon. Consequently, the rootful figures below are native Docker/amd64, not Colima/arm64. This prevents a defensible all-path Colima ratio; P9 should rerun the timing-only baseline on the intended arm64 host before using it for capacity planning.

## Rootful baseline

Only the four real Dockerfile paths have a like-for-like `docker build --no-cache` baseline. Source/static paths are generated by Railpack and cannot honestly be represented by plain `docker build` without changing the workload.

| Build path              | Rootful, s | Rootless, s | Factor |
| ----------------------- | ---------: | ----------: | -----: |
| dockerfile/web          |       1.94 |        4.88 |   2.52 |
| dockerfile-monorepo/web |       0.90 |        0.69 |   0.77 |
| java-api-frontend/api   |       5.38 |        8.24 |   1.53 |
| multi-service/web       |       0.74 |        0.63 |   0.85 |

The cold values include different pre-existing base-image caches and the first rootless frontend pull, so the 2.52 outlier is not a stable performance coefficient. Warm rootless builds are 0.34–0.69 s. The exit criterion “all examples factor <=1.5” is not proven on this VM.

## Cache, GC, failure, and concurrency

- Repeating all successful builds reduced each to 0.34–0.69 s. The Railpack examples sharing Node layers demonstrate cross-example reuse; the first Railpack build was 35.18 s and later related builds were 2.52–12.14 s.
- Cache grew to 6.23 GB. `buildctl prune --all --keep-storage 2000` reduced it to 1.63 GB and released about 4.60 GB on the VM.
- P9 recommendation: 8 GiB BuildKit PVC, GC target 2 GiB, retain records newer than 24 hours when under the target, and run `buildctl prune --all --keep-duration 24h --keep-storage 2000` after each build batch plus a scheduled daily pass. A 4 GiB PVC is too small for the observed 6.23 GB full matrix.
- A Dockerfile failing with exit 23 returned a non-zero error immediately. The next client build succeeded in 0.51 s; the builder did not hang.
- Concurrent Railpack and Python builds both succeeded in 69.15 s wall time. Individual durations were 32.64 s and 68.18 s. BuildKit reached 1132m CPU and 896 MiB memory, with zero restarts against the 2 CPU/2 GiB limit. P9 may allow two concurrent builds per pod; higher concurrency is not evidenced.

## Minimum security context

Negative-first rollout tests establish this minimum for the tested rootless image:

```yaml
spec:
  securityContext:
    fsGroup: 1000
    fsGroupChangePolicy: OnRootMismatch
    seccompProfile:
      type: Unconfined
  containers:
    - name: buildkit
      securityContext:
        allowPrivilegeEscalation: true
        appArmorProfile:
          type: Unconfined
        readOnlyRootFilesystem: true
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 1000
```

`procMount` is absent and is not required. Removing `allowPrivilegeEscalation` fails `newuidmap` with “Could not set caps”. Switching seccomp to `RuntimeDefault` fails `fork/exec /proc/self/exe: operation not permitted`. Switching AppArmor to `RuntimeDefault` is rejected with pod status `AppArmor` on the k3d node.

Important D19/P9 consequence: Kubernetes PSA Baseline allows privilege escalation and Unconfined seccomp, but its AppArmor control does not allow an explicit `Unconfined` profile. Therefore an `enforce=baseline` namespace alone cannot admit this exact minimum. P9 must choose one of: a narrowly scoped PSA exemption for the dedicated build namespace, or `enforce=privileged` with `audit=baseline` and `warn=baseline`, plus NetworkPolicy and the remaining container restrictions above. Calling the tested pod “PSA baseline compatible” would be incorrect.
